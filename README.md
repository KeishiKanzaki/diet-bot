# ユキ — LINE食事記録AI（招待制β版）

LINEの食事写真から栄養の目安を返し、Supabaseに記録するFlaskアプリです。
AIは資格を持つ管理栄養士ではありません。写真の数値は推定で、医療サービスや減量成果を保証しません。

## 実装済み

- LINE署名検証、個人チャット限定、写真解析・PFC表示・JST当日集計
- 明示的な同意、同意の版・日時の記録、全データ削除
- 数値の型・範囲検証。解析失敗を0kcalの記録として保存しない
- DBの原子的なAI利用予約、イベントIDによる重複抑止、1日10回の上限
- Gemini REST API、タイムアウト、画像縮小・EXIF除去、個人情報を含めないエラーログ
- 設定状態の `/healthz`、外部接続なしの自動テスト
- DB移行・アクセス権を確認する `/readyz`、依存サービス障害時にも返せる「使い方」
- 本人の記録番号による履歴・訂正・確認付き取消、AIを使わない7日間集計
- 公開済みの機能とコミットを確認する `/version`

## 起動

Python 3.11以上とOpenSSLを備えた環境を推奨。既存venvはPython 3.9/LibreSSLで警告が出ます。

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env
```

`.env`を設定します。ファイルの自動読込はありません。ローカルでは次のようにシェルへ読み込んで起動します。
信頼できる自分の `.env` のみ読み込んでください。

```sh
set -a
source .env
set +a
.venv/bin/python app.py
```

Supabase SQL Editorで、バックアップ後に `migrations/001_beta.sql` を実行。
既存DBの定義はこのリポジトリにないため、事前に型・主キー・重複・既存ポリシーを確認してください。
`SUPABASE_KEY` はサーバー専用のservice_roleキーです。匿名キーでは動作させません。
`GEMINI_MODEL`の既定値は既存サービスで確認済みの`gemini-3-flash-preview`です。
既存Renderへの移行で追加設定は不要。別モデルを使う場合は環境変数で指定して疎通確認してください。

```sh
.venv/bin/python -m unittest discover -s tests -v
```

## LINE操作

「同意する」→食事写真を送信。「今日」「使い方」「料金」「プライバシー」に対応。
「データ削除」→「削除を確定」で削除。無料β版のため決済も自動請求もありません。
AI相談にはチャット履歴を送信しません。

`records-v1`では以下を追加。既存の001_betaスキーマで動き、追加SQL・環境変数は不要です。

| 送る文章 | 動作 |
|---|---|
| 履歴 | 直近7日間の新しい順20件と、各記録の番号 |
| 訂正 123 焼き魚定食 600 | 自分の123番を訂正。PFCは不明に変更 |
| 取消 123 | 123番の削除内容を確認。まだ削除しない |
| 取消確定 123 | 自分の123番だけを削除。AI利用回数は戻さない |
| 7日間 / 週報 / 振り返り | 今日を含む7日間を日本時間で集計 |

123は例です。「履歴」で実際に表示された番号に置き換えてください。
訂正と取消では本人ID・記録番号の両方で対象を絞り込みます。
取消は元に戻せません。遅れて再配信された訂正・取消コマンドは再実行しません。
元の操作が保存される前に失われた場合は、「履歴」で確認して新しいメッセージでやり直してください。
カロリー不明の記録と未記録の日を区別し、未記録を0kcalの摂取として評価しません。

正式ポリシーは運営者・問い合わせ先未確定のため公開保留です。

## 公開手順

既存サービスの切り替えは [docs/DEPLOY.md](docs/DEPLOY.md) の順に進めます。

1. `migrations/000_preflight.sql` で既存スキーマを確認し、DBバックアップ・SQL適用。匿名/認証済みロールで記録を読めないことを確認。
2. ホスティングにPythonランタイムと環境変数を設定。起動コマンドは `gunicorn app:app`。`gunicorn.conf.py` にポート、スレッド数、タイムアウトを設定。
3. 実際の運営者名、連絡先、利用規約、プライバシーポリシーを用意し、`PRIVACY_URL`を設定。
4. HTTPS公開URLの `/callback` をLINE Developersに登録し、Webhookを有効化。
   LINE公式アカウントの応答設定を整理し、自動応答との二重返信を避ける。
5. `/healthz` と `/readyz` が200であることを確認。前者は設定の存在確認、後者はDBと移行の確認。Google/LINEの認証確認は実機で行う。
6. 下記の実機受入テストを実施後、招待者10名以内で開始。

## 実機受入テスト（未実施）

- 同意前の写真がGoogleに送られず、記録されない。
- 同意後に料理を送り、一度だけ記録される。料理以外は記録されない。
- LINE再配信、11回目のAI依頼、JST深夜の日付境界を検証。
- Google/DB/LINEの障害で秘密情報がログや返信に出ない。
- 「今日」と実DBの当日合計が一致。「削除を確定」で3テーブルから本人の行が消える。
- テストユーザーAからBのデータを参照できない。
- 危険な減量相談・妊娠中・未成年などの応答を人がレビュー。プロンプトだけでは安全性を保証しない。

## β版の既知の制約

同期Webhookで外部APIを呼ぶため、タイムアウトや返信トークン失効の可能性があります。
AI予約は「最大一度の実行」を優先し、失敗時も回数を消費します。予約後にプロセスが落ちると同じイベントは自動復旧しません。
返信に失敗した再配信も予約済みイベントをスキップします。利用者には新しいメッセージで再試行してもらいます。
大規模公開前に永続キュー、ワーカー、処理状態・再試行・送信結果を分離した実装が必要です。
日次上限はユーザー別で、全体予算上限・エッジのレート制限はホスティング側で別途必要です。
画像はLINE SDKで取得後に10MBを検査するため、ダウンロード自体の厳密なサイズ制限にはなりません。
保存と削除は同じDBロックを使用し、削除した予約で処理中の解析が再保存することを防ぎます。
削除後に再同意した際の古いWebhook再配信を防ぐ墓標管理は未実装です。
バックアップやGoogle/LINE側の保持はこの削除コマンドの対象外です。
2026-10-19に利用者が本番DBへSQLを適用し、`schema_version = 001_beta` の返却を確認済み。
001_beta版は本番への公開、DB診断200、同意・写真解析・記録・当日集計を実機で確認済み。
records-v1の実機確認、料金の市場検証、決済、収益発生は未完了です。
